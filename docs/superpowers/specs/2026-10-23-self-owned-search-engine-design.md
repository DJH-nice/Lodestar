# 自研搜索引擎设计（替换上游 FSearch）

> 生成时间：2026-10-23 · 分支 `master`
> 决策来源：用户明确要求「把 Sextant 的上游给换了，因为是别人的开源代码」
> 配套实施计划：待本设计确认后另出 `plans/2026-10-23-self-owned-search-engine.md`

---

## 0. 一句话说清这次变更

**把「复用上游 FSearch 的 C 引擎 + C 垫片」换成「完全自研的 Rust 搜索引擎」**，
图形界面（Vue 前端 + Tauri 外壳）保留不动。

| | 现在（复用上游） | 之后（自研） |
|---|---|---|
| 引擎 | 上游 FSearch 0.3.2 的 C 引擎子集（GPL-2.0-or-later） | 自研 Rust 引擎（自有版权） |
| 边界层 | `shim/`（13 个 C 函数的 FFI） | Rust crate（无 FFI） |
| 依赖链 | GLib / GIO / Pango / PCRE2 / **ICU** | 纯 Rust：`regex` / `unicode-normalization` / `unicase` / `memmap2` / `notify` |
| 许可证义务 | 必须随包分发**完整对应源码**（13MB） | **无** |
| `.app` 体积 | **60M**（ICU 34M + 源码包 13M + 其余 13M） | **目标 8–12M** |
| 冷启动 | 300–450ms（每次全量扫描） | **目标 5–15ms**（mmap 读档） |
| 热缓存扫描 | 74.6ms | **目标 20–30ms**（并行遍历） |
| 查询延迟 | 0.14–2.7ms | **目标 ≤1ms**（索引期折叠，见 §4.3） |
| 实时更新 | 全量重扫 | **增量 <5ms** |

## 1. 为什么换（三个真实收益，不是换口味）

### 1.1 许可证

上游是 GPL-2.0-or-later，本项目分发它 → 是衍生作品 → 必须随包分发完整对应源码
（现在 `Resources/licenses/` 里压着一个 14MB 的源码包，占 `.app` 的 22%）。
自研引擎没有这个问题，`.app` 直接瘦一圈，且不再需要在 README / 致谢面板里维护
GPL 出处与修改说明。

### 1.2 性能天花板

上游引擎的搜索是 **O(N) 全表线性匹配**，且**每次查询都在匹配期做 Unicode 折叠**
（`fsearch_utf.c` 的 `ucasemap_utf8FoldCase` + `unorm2_getNFDInstance`）。
实测代价：

| 数据 | 上游查询耗时 |
|---|---|
| 合成索引 100,002 项，命中 10 条 | **0.99ms** |
| 真实 `$HOME` 8,352 项，命中 0 条 | 0.14ms |
| 真实 `$HOME` 8,352 项，命中 55% | **2.6ms** |

同一个引擎、同样的匹配逻辑，合成数据比真实数据快 **18 倍** —— 差额就是
「真实文件名要折叠、合成名字不用」。**把折叠从匹配期挪到索引期**，
是自研引擎能拿到的最大单点提速（§4.3）。

### 1.3 体积

`.app` 60M 里，**ICU 一家 34M**（`libicudata.78.dylib` 32M + `libicuuc` 1.8M）。
ICU 是因为上游直接调用了 `unicode/ucasemap.h` / `unicode/unorm2.h`。
自研引擎用纯 Rust 的 `unicase` + `unicode-normalization` 替代 →
**没有 ICU，没有 GLib，没有 Pango，没有 PCRE2，没有 34M 的数据文件**。

## 2. 性能基线（全部实测，探针可复现）

探针源码在 `/tmp/fsprobe/`（`walk.c` / `walk_par2.c` / `scale.c` / `scale2.c` / `sortcost.c`），
链 `build-shim/libfsearch_shim.dylib` 跑真实引擎。

### 2.1 扫描（`$HOME`，8,352 条目，排除规则同引擎）

| 场景 | 实测 |
|---|---|
| 裸遍历（`readdir`，不 stat） | 151.7ms |
| 遍历 + `fstatat`（引擎要的量） | **270.8ms** |
| ├ stat 增量 | 119.1ms（占 44%） |
| 上游 C 引擎扫描（冷缓存） | 300–450ms |
| 上游 C 引擎扫描（热缓存） | **74.6ms** |
| 裸遍历 1 线程（热缓存） | 38.1ms |
| 裸遍历 2 / 4 / 8 线程（热缓存） | 22.2 / **16.6** / 15.5ms |

**结论**：
- 上游扫描 ≈ 裸 IO 地板的 2 倍（差额是建条目 + 5 维预排序数组）。
- **并行遍历能把地板从 38.1ms 打到 16.6ms（2.3×）**，且 4 线程就饱和。
- 冷缓存下受磁盘延迟支配，并行收益被 I/O 吃掉一部分，但仍然显著。

### 2.2 查询

| 场景 | 实测 |
|---|---|
| 合成 10,002 项 | 0.21ms |
| 合成 50,002 项 | 0.54ms |
| 合成 100,002 项 | **0.99ms**（≈10ns/条目） |
| 全量匹配 `*`（100,002 项） | 2.68ms |
| 切排序维度首次搜索 | 0.95–1.06ms（**无冷启动惩罚**） |
| 翻页（不重跑匹配） | 0.33ms |

**结论**：上游的线性匹配**常数极小**（10ns/条），**不要造倒排索引**。
1M 条目 ≈ 10ms，仍然无感。自研引擎照抄「线性 + 提前退出」即可。

### 2.3 目录规模的一个残酷事实

`~/Library` 一个目录 = **264,800 条目**（≈ 32× 于可见目录总和 8,320）。
排除规则是**目录级剪枝** —— 不剪枝就等于每次扫描多扫 26 万条。

> ⚠️ 探针踩过的坑：第一版并行探针在**顶层**漏了排除规则，
> 结果 8,320 条目变成 273,415 条目、耗时从 0.49s 变成 10.7s。
> **排除规则必须在每一层生效，包括顶层。**

## 4. 核心设计决策

### 4.1 存储格式：mmap 列存 + 字符串 arena

单文件 `index.v1`，mmap 只读打开：

```
┌──────────────────────────────────────────────┐
│ header (128B)                                │
│  magic "LDSI" | version | counts | offsets    │
├──────────────────────────────────────────────┤
│ entry table: N × 32B 定长记录                 │
│  parent_id u32 | name_off u32 | name_len u16   │
│  path_off u32 | path_len u16 | flags u8       │
│  size u64 | mtime i64 | depth u16             │
├──────────────────────────────────────────────┤
│ name arena: 变长 UTF-8（原始名）                │
├──────────────────────────────────────────────┤
│ folded arena: 变长 UTF-8（NFD + 大小写折叠）     │
├──────────────────────────────────────────────┤
│ path arena: 变长 UTF-8（完整路径）              │
└──────────────────────────────────────────────┘
```

**为什么存完整路径**（上游不存、运行时走父链重建）：
- `path:` 查询是高频操作，走父链 = 每条目 O(depth) 拼接。
- 存全路径的代价可算：8,352 条目 → name 166KB + folded 180KB + path 500KB
  + 定长表 266KB ≈ **1.1MB**（当前引擎是 4.3MB）。
- 父 id 仍然保留，给 `depth` / `childcount` / 树形操作用。

**为什么排序不预存 5 份数组**（上游存 5 维）：
- 只维护 1 份「按 name 排序的 id 数组」（u32 × N = 33KB@8K / 400KB@100K）。
- 其余维度（path / size / mtime）按需排序**当前结果集**，而不是全表。
- 结果集通常远小于全表（翻页只要 500 条）→ 排序成本从 O(N log N) 降到 O(M log M)。

### 4.2 冷启动：mmap 读档

启动 = `mmap` 索引文件 + 读 header → **立即可搜**，不等扫描。
文件被原子替换（temp + rename）后重新 mmap 即可。

代价：mmap 的页是**按需换入**的 → 第一次查某个区域会有一次 page fault。
8,352 条目 ≈ 1.1MB → 几十次缺页，微秒级。

### 4.3 查询：折叠前移到索引期（最大的单点提速）

**上游做法**：查询时对每个条目做 ICU 折叠 + NFD 归一化 → 真实数据慢 18×。

**自研做法**：
1. **索引期**：对每个 name 存两份 —— 原始名 + `folded`（NFD + case-fold）。
2. **查询期**：查询串折叠**一次**（几十纳秒），然后字节比较。
3. 匹配判定用 folded 名 → O(1)/条目，无分配。
4. **高亮区间**：折叠会丢失原串偏移 → 只对**当前页的 500 条**回到原始名上做
   一次大小写不敏感定位，拿到字节区间。500 × 短名字 = 微秒级，可忽略。

**Rust 侧 Unicode 方案**（替掉 ICU）：
- `unicode-normalization`：NFD 归一化（对应上游 `unorm2_getNFDInstance`）。
- `unicase`：case folding（对应上游 `ucasemap_utf8FoldCase`）。
- 两者纯 Rust、静态编译进二进制、约 1–2MB 静态表 —— **不需要 34M 的 ICU 数据文件**。

> ⚠️ 语义要对齐上游：**NFD 而非 NFC**。APFS 不做归一化，
> 同一文件可能以 NFD/NFC 两种形态出现 → 折叠用 NFD 可以让两者匹配上。

### 4.4 匹配算法

| 查询形态 | 策略 | 复杂度 |
|---|---|---|
| 纯前缀（`abc`） | 按 name 排序数组上二分定位起点 → 线性扫该段 | O(log N + K) |
| 子串（`ab*c`） | 全表线性 + 首字节早退 | O(N)，实测 10ns/条 |
| 通配（`*.rs`） | 转成 `regex` crate 的 pattern（线性时间引擎，无回溯爆炸） | O(N) |
| 正则（`/re/`） | `regex` crate，**不是 PCRE2**（Rust regex 保证线性时间，无灾难性回溯） | O(N) |
| 字段（`size:>1M`） | 字段判定不碰字符串，直接读定长记录 | O(N) 但极快 |
| 多词 AND | 逐词求交集（位图） | O(N/64) 交集 |

### 4.5 查询语法（**自研，不照抄上游**）

上游 parser 是 GPL 代码，**不能抄**。能力对齐、语法自定：

| 能力 | 上游 | 自研设计 |
|---|---|---|
| 词 | 空格分隔 | 空格分隔，双引号包裹短语 |
| 逻辑 | `AND` / `OR` / `NOT` / 括号 | `&&` `\|\|` `!` 括号 + 关键字别名 |
| 字段 | `ext:` `size:` `dm:` `depth:` `contenttype:` `parent:` | `ext:` `size:` `mtime:` `depth:` `kind:` `path:` `name:` |
| 比较 | `=` `:` `<` `<=` `>` `>=` | 同上 + `!=` |
| 通配 | `*` `?` | 同上 |
| 正则 | 修饰符 `regex:` | `/.../` 定界符 |
| 大小写 | smart case（有 uppercase→敏感） | 同上（保持用户习惯） |
| 路径 | 含 `/` 自动搜路径 | 显式 `path:` + 自动（保持习惯） |

**单一真相**：语法表由新引擎导出（`syntax_tables` command 继续存在），
手册 / 速查表 / 前端高亮共用同一份 —— 沿用现有 `app/shared/syntax-tables.json` 流程。

### 4.6 增量更新

```
FSEvents(notify 8.2.0，已在依赖里)
   → 脏目录集合（去抖 800ms，沿用现有 watcher 的参数）
   → 只重扫脏目录子树
   → diff：新增条目追加、消失条目打墓碑、变更条目改 mtime/size
   → 原子替换索引文件
```

对比现状：**全量重扫（50ms）→ 增量（<5ms）**。
增量更新用「脏目录重扫 + diff」而不是逐事件增删 —— 前者实现简单、后者容易漏。

### 4.7 排除规则

- 内置：隐藏目录（basename 以 `.` 开头）、`Library`、`Applications`、`target`、`node_modules`。
- 用户可配：设置面板里加「排除规则」页（当前缺口项之一，顺手补上）。
- **目录级剪枝**：命中规则的目录不递归进去。
- 规则命中要**逐层判断**（顶层也要判）—— §2.3 的坑。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **查询语法与上游不一致** | 老用户迁移后查询写法要改 | 能力对齐 + 语法表单一真相 + 手册给出对照表；保留 `AND/OR/NOT` 关键字别名降低迁移成本 |
| **Unicode 语义漂移**（`unicase` 与 ICU 折叠差异） | 大小写不敏感匹配结果不同 | 用 `unicase` 的 full case folding；建一批对照用例（中文/土耳其语 i/德语 ß/组合字符） |
| **mmap 文件被外部替换** | 段错误 / 读到旧数据 | 只读 mmap + 文件句柄持有 + 校验 header magic/version；替换走 temp+rename 并重新 mmap |
| **大目录（`~/Library` 26 万条目）** | 扫描爆炸 | 排除规则默认生效 + 顶层也判 + 设置面板可观测「排除了什么、排了多少」 |
| **增量漏更新** | 索引与磁盘不一致 | 脏目录重扫（不是逐事件）→ 漏不掉；另加周期性全量校验（可选，默认关） |
| **GPL 残留** | 误抄上游代码 | 移除 `src/` + `shim/` 后做一次全仓检索（`g_assert`/`fsearch_`/`pcre2`/`ucasemap` 等标记） |
| **前端回归** | 破坏已有 266 个用例 | command 契约保持不变；M2 验收要求前端零改动通过 |

## 8. 需要拍板的点

1. **查询语法**：能力对齐上游但语法自定（本文 §4.5），还是**直接沿用上游写法**以零迁移成本？
   ⚠️ 沿用写法本身不抄代码，但语法表若是「照抄上游的表达形式」，建议只保留
   `AND/OR/NOT` 关键字与 `ext:`/`size:` 这类**通用惯例**（这些是行业通用写法），
   其余自定。
2. **是否保留 `shim/` 与 `src/` 的历史**（只从构建里摘掉 vs 从仓库里删掉）：
   删掉后 GPL 义务彻底消失，但失去「对照参考」；建议**删**（保留一份压缩包在
   仓库外），并同步重写 AGENTS.md 的硬约束。
3. **是否顺带补上当前的 UX 缺口**（⌘K 命令面板、浅色主题、QuickLook、
   可配置排除规则、`~` 展开、MiB/GiB）：这些与引擎无关，但改动小、用户感知强。
4. **旧设置迁移**：`settings.json` 里的索引目录 / 书签 / 快捷键要不要留，
   还是借换引擎的机会清空重来（建议保留索引目录，其余保留即可）。
